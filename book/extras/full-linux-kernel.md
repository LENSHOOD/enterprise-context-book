# 番外：为完整 Linux 内核建立代码知识库

第 18 章以 eBPF 子系统说明代码知识库的基本方法。本番外把同一问题放大到完整 Linux `v6.12`。计数口径如下：`tracked_paths=86,680` 是 `git ls-files` 返回的全部路径；`ingested_files=64,882` 是进入工具 scope 的源码或文档；其中约 `61,390` 个属于代码扩展名，其余是进入 scope 的文档和构建材料。三者不是可直接相加的独立集合。

实验固定 tag `v6.12` 和提交 `adc218676eef25575469234709c2d87185ca223a`。Linux 源码不进入书籍仓库，所有知识对象引用均包含这个提交。配套命令、fixture 与完整统计位于案例目录的 `FULL_KERNEL_REPORT.md`。

## 1. 为什么不能把 eBPF 脚本直接指向仓库根目录

eBPF 子图只处理 97 个文件时，可以把节点、边和正文保存在内存并输出 JSON。完整内核若照搬这条路径，会同时遇到四种放大。

第一是对象规模。一个 C 文件不只产生一个文档块，还会产生函数、类型、宏、配置、测试与调用候选。第二是关系扇出。公共 helper、头文件和构建配置会连接大量子系统，任意两跳都可能膨胀。第三是版本。全仓提交频繁，重建所有摘要和向量既昂贵又制造噪声。第四是解析不确定性。宏、条件编译、架构差异和函数指针在全仓中不再是边缘情况，而是代码组织方式本身。

第一次全仓尝试验证了这一点。它把类型使用误作定义，并为每个调用候选单独查询同名定义。约八分钟后仍没有完成关系解析，数据库与 WAL 已超过 3 GB。失败不是机器不够快，而是算法把“小图上可以接受的方便”放大成了全局开销。

## 2. 全仓对象模型

这里的“对象模型”不是把解析器产生的所有节点直接称为本体。按照第 8 章的三层区分，路径、构建、维护、语义和知识是概念视图；稳定 ID、类型、关系、证据等级与时间构成逻辑模型；SQLite 表、FTS5 和后续图存储只是物理投影。这个区分允许未来用 Tree-sitter 替换正则、用 SCIP 补充符号关系，而不改变 `Symbol`、`DEFINED_IN` 或 `MAINTAINED_BY` 的领域含义。

完整内核至少需要五类互相重叠的视图。

路径视图从顶层目录开始，把 `drivers/gpu`、`drivers/net`、`fs/ext4`、`arch/x86` 等作为路由与容量分片。构建视图来自 Kbuild、Makefile 和 Kconfig，表达对象在什么配置与架构下进入产物。维护视图来自 MAINTAINERS，连接子系统、文件模式、邮件列表与负责人。语义视图包含文件、函数、类型、宏、定义和引用。知识视图连接 Documentation、注释、提交、测试和生成 Wiki。

这些视图不能压成一棵树。例如 `include/linux/rcupdate.h` 位于 include 路径，由 RCU 维护者负责，被多种构建目标使用，又被大量子系统引用。路径树适合导航，图适合跨视图连接，Wiki 适合阅读，ArtifactFS 负责最终源码证据。

统一对象信封仍然适用：逻辑 ID、提交版本、路径和行、解析器与配置、证据等级、输入散列。一次查询必须固定 Snapshot Manifest，不能把 `v6.12` 的 Wiki 与主分支代码图融合。

## 3. 流式 SQLite 基线

配套工具新增 `ingest-full`。它不把全仓图放在 Python 内存中，而是逐文件写入 SQLite。源码和文档生成 file/document 节点，C 解析生成函数与类型候选，原始调用先进入暂存表。扫描结束后，系统一次性聚合 `name → 定义数量与目标 ID`，只有全仓名称唯一的函数进入 `CALLS_NAME_RESOLVED`，其余保留 `CALLS_CANDIDATE`。

FTS5 为节点名称、路径与有限正文建立词法索引。查询先接受子系统过滤，再在局部范围检索，命中对象作为图扩展种子。这个实现仍是 syntax-only 基线，却验证了三个可扩展契约：摄取可流式提交，关系可分阶段解析，查询不必加载全图。

以下数字来自 2026-08-23 的 syntax-only 单机一次运行，不是性能基准；机器可读转录位于 `examples/linux-ebpf-case/reports/full-kernel-run.json`，原始数据库和运行日志未提交，因此仍不能视为独立复现证据。该运行用时 175.809 秒，其中扫描与写入 137.970 秒；纳入 64,882 个文件，生成 1,544,788 个节点和 5,601,741 条边；SQLite 文件约 3.6 GB。1,676,138 条调用通过“全仓名称唯一”解析，2,436,142 条仍是模糊或缺失候选。

这些数字不能当作代码事实。尤其是 1,352,851 个函数候选显著偏高，说明正则将宏和复杂声明误判为函数。大规模实验的价值恰恰是让误差可见：若只展示命中的几个正确符号，很容易把高召回误认为高精度。

## 4. 子系统分区效果

路径投影中，`drivers/gpu` 包含 6,776 个文件，`drivers/net` 有 5,637 个，`include` 有 6,204 个，`tools` 有 4,156 个。单个一级分区的规模已经超过很多独立企业仓库。全内核不应只有一个向量集合和一张无边界图。

合理的物理分区可以按 release、架构和子系统组织。逻辑查询则允许跨区：先在 `kernel` 找到 eBPF syscall，再沿确定依赖进入架构 JIT；先在 `fs/ext4` 找到写入路径，再连接通用 block 和 journaling；先在 `drivers/gpu` 找到 DRM atomic helper，再进入具体厂商驱动。

子系统路由不能成为不可恢复剪枝。公共头文件、核心库和跨目录接口应进入共享索引；精确符号查询也应能绕过错误路由。规划器可以先选两个或三个分区，再根据图边按预算扩展。

## 5. 六组实际查询

在同一份 3.6 GB SQLite 快照上，本地 CLI 的六组查询耗时为 0.07–0.33 秒。这不是严谨性能基准，因为没有控制缓存和硬件，但足以观察检索形态。

调度查询 `schedule wake_up_new_task pick_next_task_fair` 将两个目标函数排在前二；ext4 查询命中 `do_journal_get_write_access` 与多个 inode/journal 入口；TCP 查询集中于 `tcp_input.c` 与 `tcp_cong.c`；DRM 查询命中 `drm_atomic_commit` 和 atomic helper；eBPF 查询命中 `bpf_check`、`bpf_prog_load` 与 `verifier.c`；RCU 查询命中 `synchronize_rcu` 及 tasks/tree 路径。

结果也暴露明显缺陷：调度、ext4、eBPF 与 RCU 首屏出现名为 `if` 的伪函数。实验后，工具已在摄取和查询层过滤 C 控制关键字，但更深的宏误识别仍需语法解析器解决。TCP 与 DRM 的词法结果较干净，是因为查询包含高度区分的领域前缀和函数命名。

这说明 BM25 在全仓仍然不可替代。用户知道符号、文件或子系统术语时，词法通道快且准确；向量更适合“不知道内核叫什么”的概念问题；图负责从入口沿定义和依赖扩展；Wiki 提供机制级解释。四者是协作关系。

## 6. 为什么 3.6 GB 仍然太大

实验把有限源码片段同时保存在对象表和 FTS 中，因此索引接近工作树体积的两倍。这对研究原型可以接受，对多 release、多个架构的长期知识库不可接受。

正式架构应将 Git 或 ArtifactFS 作为源码 blob 层。结构索引只保存对象 ID、名称、路径、行、签名、内容散列和短摘要；需要实现时按提交读取源码。词法索引可以保存符号、注释和有限窗口，不复制整个函数。向量只覆盖模块摘要、文档段落和高价值符号解释，而不是机械地为每个 AST 节点生成嵌入。

历史 release 使用冷热分层。当前 LTS 与主开发线保持完整结构和热索引，旧版本保留对象清单、差异和按需索引能力。内容散列让跨版本未变化对象复用摘要与向量，但证据 URI 仍绑定各自提交。

## 7. 从 syntax-only 到编译级图

全仓知识图应标明精度层。第一层 Tree-sitter 恢复函数、类型、宏和语法调用，解决 `if` 等明显误识别并支持增量解析。第二层读取 Kconfig 与 Kbuild，为节点和边增加架构、模块和配置条件。第三层用 clang、语言服务器或 SCIP 固化定义与引用。第四层从 BTF、符号表和构建产物验证进入目标内核的类型与函数。第五层用 ftrace、perf 或 eBPF 观察特定运行路径。

静态“可能调用”与运行“曾经调用”不能互相覆盖。一个边可以同时拥有语法、编译和运行证据，查询按任务风险选择。源码研究允许使用候选边探索；变更审批要求编译配置和测试证据；性能诊断还需要运行观察。

函数指针和宏不会被某个单一解析器彻底消除。系统应把 unresolved 当作产品能力：显示目标名、歧义候选、配置和补充验证方式。隐藏不确定性只会制造一张错误但漂亮的调用图。

## 8. Wiki 不应覆盖每个符号

若为 154 万节点逐一调用模型生成页面，成本、更新噪声和错误数量都会失控。全内核 Wiki 应从高层地图开始：内核启动、调度、内存管理、VFS、网络、驱动模型、同步、跟踪与安全。第二层对应子系统和构建目标，第三层对应高中心性模块与公共接口，符号层主要由模板和按需解释提供。

页面优先级可以由文档缺口、查询热度、变更频率、依赖中心性和维护者选择共同决定。自动摘要记录输入文件、提交、配置和生成版本。公共头文件变化时只使依赖页面 stale，不立即重写全站；冷门符号首次被研究时再生成临时解释，经复用和审核后晋升。

这种设计把 Wiki 从“全仓逐文件摘要”变成“按认知价值编译的多层地图”。源码仍然是事实，Wiki 是可失效的解释缓存。

## 9. 面向个人研究者的实施路径

第一步固定一个 LTS tag，建立 Git/ArtifactFS 与 BM25，保证所有结果可回到源码。第二步按路径、MAINTAINERS、Kconfig 和 Kbuild建立子系统目录，先服务精确定位。第三步为关注子系统增加 Tree-sitter 与编译索引，不必一次覆盖全部语言和架构。

第四步选择二十到五十个真实研究问题，标注入口、必要路径和源码证据。问题应覆盖机制解释、定义/注册/调用、配置差异、变更影响和跨版本演进。第五步只为这些任务加入图扩展与层级 Wiki，用消融证明它们相对 BM25 的收益。

对作者而言，可以从 eBPF、调度器、RCU、内存管理或网络栈逐个建立高精度子图，同时让全仓 SQLite 提供低成本背景检索。高精度岛屿通过统一符号和提交连接到低精度海洋。这样既能立即研究整个内核，又不会假装全仓关系已经同等可信。

## 10. 本次实验回答了什么

完整 Linux 知识库在单机上是可建模和可搜索的，真正难点不在存下文件，而在控制对象身份、关系精度、索引复制和知识维护。路径分区与词法检索提供了可用底座；SQLite 流式实现证明百万节点和数百万边可以在几分钟内构建；六组查询证明精确符号与领域词能够快速定位。

同一实验也否定了三个诱人方案：不能把正则抽取数量当作理解程度，不能把所有源码复制进每种索引，不能为每个符号生成 Wiki。完整架构应是“全仓低成本地图 + 重点子系统高精度图 + ArtifactFS 源码 + 分层 Wiki + 多通道检索 + 可见误差”。

这比声称已经读懂 Linux 更有价值。它给出了一个可以持续演进的研究系统：每增加一种编译配置、一个子系统或一组 Golden Questions，知识库的可信范围都能被明确扩大和重新评测。

## 复现命令

```bash
cd examples/linux-ebpf-case
python3 -m linux_kb ingest-full \
  --repo /path/to/linux \
  --ref v6.12 \
  --database generated/linux-v6.12.db
python3 -m linux_kb report-full \
  --database generated/linux-v6.12.db
python3 -m linux_kb query-full \
  'drm atomic commit' \
  --database generated/linux-v6.12.db \
  --subsystem drivers/gpu
```

完整实验数字和已知误差参见配套案例的 `FULL_KERNEL_REPORT.md`。Linux 官方源码与文档分别见 [kernel.org](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git) 和 [Linux Kernel Documentation](https://docs.kernel.org/)。
