# 第 11 章 来源、版本、时间与统一对象模型

> 本章要回答：如何让来源、版本、时间和删除语义在所有知识投影中保持一致？

企业知识问题经常表面上像检索问题，实际是身份和时间问题。“退款期限是多少”可能有全球规则、地区例外、旧版本和即将生效版本；“这个函数在哪里定义”必须绑定仓库提交；“谁负责支付系统”会随组织调整变化。若平台只保存文本和向量，它无法判断两条结果是重复、冲突还是历史演进。

统一对象模型为所有来源建立共同的最小语义，使原文、分块、摘要、图节点、向量和记忆能够指向同一对象。它不试图把企业所有业务数据塞进一个万能 Schema，而是定义跨知识类型都必须具备的身份、版本、时间、来源、权限和血缘。

## 11.1 来源对象、逻辑对象与版本对象

平台至少要区分三个身份。来源对象是外部系统中的原始记录，例如 Confluence 页面 ID、Git 路径、工单号或数据库表。逻辑对象是企业语义中的持续实体，例如“退款政策”或“退款服务”。版本对象则绑定一次不可变内容和状态。

逻辑 ID 用于跨时间跟踪。政策从 v2 更新到 v3，它仍是同一逻辑对象；文件移动但符号身份未变，也可以维持关系。证据 ID 必须绑定版本，因为引用“退款政策”不足以复现答案，必须引用“退款政策 v3 第 4.2 条”。

来源对象与逻辑对象不是一对一。一项业务概念可能由多个来源共同描述，一份文档也可能包含多个对象。解析层要保留这种映射，不应为了方便强制把每个文件当作一个知识实体。

稳定 ID 可以由租户、来源系统和源 ID 规范化生成，也可以使用内部 UUID 配合唯一映射表。内容散列不能单独充当逻辑身份：两个对象可能内容相同，同一对象也会随编辑改变散列。散列适合判断内容版本与去重。

## 11.2 最小对象信封

不同对象拥有不同正文结构，但可以共享一个“信封”。下面是简化示例：

```json
{
  "object_id": "ko:northstar:policy:refund",
  "version_id": "kv:sha256:8f...",
  "kind": "policy_section",
  "tenant": "northstar",
  "source": {
    "system": "git",
    "uri": "repo://handbook/refund.md",
    "revision": "3ab41e7",
    "locator": "section-4.2"
  },
  "time": {
    "valid_from": "2026-08-01T00:00:00Z",
    "valid_to": null,
    "observed_at": "2026-08-01T00:03:12Z"
  },
  "acl": {"policy_id": "acl:support-emea"},
  "lineage": {"derived_from": [], "transform": "markdown-parser@1.4"},
  "content_hash": "sha256:8f..."
}
```

`kind` 决定正文 Schema，`tenant` 和 ACL 决定安全域，`source` 提供回跳和版本定位，`time` 表达有效性与采集，`lineage` 记录转换。对象还可以带所有者、敏感级别、语言、质量状态和保留策略。

信封应在解析后立即建立，并贯穿所有投影。向量记录只保存 `version_id` 和嵌入，图节点保存对象 ID 与图属性，Wiki 声明保存证据版本，检索结果再通过对象服务还原完整信息。这样可以避免每个后端复制并逐渐漂移一套元数据。

## 11.3 双时间：事实何时成立，系统何时知道

业务有效时间与系统采集时间不能混淆。退款政策可能 8 月 1 日生效，但连接器因故障到 8 月 3 日才同步。`valid_time` 表示事实在业务世界中何时成立，`system_time` 或 `observed_at` 表示平台何时记录它。

回答“8 月 2 日按规定应该怎样处理”需要选择当日有效政策，即使平台当时尚未同步；审计“8 月 2 日智能体为什么给出旧答案”则必须恢复当时系统实际可见的版本。两类问题使用不同时间轴。

双时间也适用于组织、图关系与实时观察。某团队从 9 月起负责服务，系统 8 月中已录入这次未来变更；调用关系在提交中出现，但直到部署后才进入生产。只保存单个更新时间，会把计划、事实与观察混成一件事。

时间查询应成为 Context API 的显式参数，而不是从自然语言隐式猜测。缺省可以是“当前有效且当前已知”，历史复盘则指定业务时间和知识快照。

## 11.4 来源权威性与冲突

企业来源天然冲突。服务目录写着团队 A，README 写着团队 B，最近事故由团队 C 值班。平台不能简单采用“最后更新者”，因为不同来源可能描述不同责任；也不能让模型根据措辞自信程度选择。

冲突处理从来源契约开始。每类声明指定规范系统，例如组织汇报关系来自 HR，生产所有权来自服务目录，接口定义来自固定提交的 OpenAPI，业务规则来自已发布政策。其他来源仍可被检索，但标记为解释、观察或潜在冲突。

适用范围也必须参与判断。中国区与欧洲区政策并非冲突，前提是对象保存地区限定；旧 ADR 与当前实现也可能是历史关系。只有在相同主体、属性、有效时间和适用范围内出现不同值，才构成真正冲突。

无法自动解决的冲突应成为一等结果。上下文包可以返回双方声明、来源、权威等级和缺失信息，要求用户或所有者判断。静默覆盖会让知识库看起来整洁，却丢掉了最需要治理的信号。

## 11.5 派生知识的血缘

分块、嵌入、摘要、Wiki 页面、实体和图边都由来源转换而来。血缘记录“由什么、通过什么过程、在何时生成”。W3C PROV 提供了实体、活动与 Agent 的通用溯源数据模型，可作为设计参考。[W3C PROV-O](https://www.w3.org/TR/prov-o/)

企业平台不一定实现完整标准，但至少应记录直接输入版本、转换器、配置、模型与提示版本、输出版本和运行 ID。对一个 Wiki 结论，应能下钻到页面生成任务，再到使用的源片段；对一条推断图边，应能看到抽取文本和解析器。

血缘支撑四类操作：来源变化后的影响分析，错误生成物的撤回，模型或解析器升级后的定向重建，以及审计回答中的声明。没有血缘，任何质量问题都会退化成全量重建和人工猜测。

## 11.6 变更检测与幂等摄取

连接器可能重复发送事件、乱序到达或漏掉更新。摄取任务必须幂等：相同来源修订和转换版本重复执行，得到同一版本对象，不制造重复节点。内容散列帮助识别无语义变化，来源游标与定期对账帮助发现遗漏。

变更可以分为内容、元数据、权限和删除。正文未变但 ACL 收紧时，不必重算嵌入，却必须立即更新所有服务路径和缓存；标题移动可能只更新定位；正文变化则创建新版本并使派生物过期。分类处理降低成本，也避免安全更新被排在昂贵模型任务之后。

大规模来源适合使用事件与周期扫描结合。事件提供低延迟，扫描恢复漏事件并验证完整性。每次批次形成清单：读取了哪些源修订，产生了哪些对象，哪些失败，是否达到发布质量门槛。

## 11.7 删除是知识生命周期的一等事件

“删除源文档”不等于“向量库以后不再更新”。已删除内容可能仍存在于分块、向量、图、Wiki、查询缓存、评测样本和任务记忆中。平台需要一条可追踪的撤销传播链。

删除首先建立 tombstone，保留最小身份、删除时间和原因，以防迟到事件让对象复活。随后撤销可服务版本，删除或隔离索引投影，使依赖页面过期，清理缓存，并按法规和备份策略安排物理清除。审计日志可保留“发生过删除”而不保留被删正文。

权限收回与删除不同。对象仍存在，但某些主体不再可见；派生摘要若混合了多个权限域，可能需要重建或下线。删除传播测试应成为安全回归的一部分：给定一个源对象，系统能列出并验证其所有派生副本已不可访问。

## 11.8 快照、发布与回滚

摄取完成不等于立即上线。数据面先构建候选快照，运行完整性、权限、引用和金标准测试，再由控制面发布 Manifest。读请求只访问已发布版本，构建中的半成品不会泄露到生产。

快照可以使用 copy-on-write、版本表或不可变索引别名实现，具体技术取决于后端。关键契约是原子切换和保留上一可用版本。若新图缺少大量边或新嵌入使召回下降，控制面可以回滚整个兼容集合。

对于实时状态，完整快照并不现实。它们以带 `observed_at` 和 TTL 的工具结果进入上下文，不与稳定知识假装拥有同一一致性模型。Context API 应同时返回知识 Manifest 和各实时观察时间。

## 11.9 Northstar 的版本冲突

Northstar 的退款政策 v3 将期限从 30 天改为 14 天，生效日是 8 月 1 日。连接器同日摄取政策，但一个旧 Runbook 仍写 30 天。统一对象模型把两者识别为不同类型：政策是该规则的规范来源，Runbook 是处置说明。冲突检测生成知识差异项，而不是用新政策静默重写手册。

客服询问当前规则时，系统引用政策 v3，并提示 Runbook 待更新；审计 7 月工单时，系统按业务有效时间选择 v2；审计 8 月 1 日上午的旧回答时，则使用当时发布的 Manifest，解释系统为何尚未看到 v3。三种答案都可以被版本和时间证据复现。

Runbook 更新并审核后，新快照发布，旧版本继续用于历史复盘。所有引用都绑定版本，因而不会因为页面地址未变而指向后来内容。

配套 Northstar fixture 把这一边界变成了可运行断言：`documents_as_of(valid_at, observed_at)` 先按政策的业务有效区间选择版本，再排除当时尚未被系统观察到的对象。测试分别验证变更前、变更后和“业务上已生效但系统尚未摄取”的结果。这个最小接口只保存对象的首次观察时间，不能重建之后发生过的每次系统时间变更；生产审计仍必须读取当时发布的不可变 Manifest，而不能用今天的索引倒推历史认知。

## 本章小结

统一对象模型不是统一所有业务 Schema，而是为知识对象建立共同信封。逻辑 ID 跟踪持续实体，版本 ID 固定证据，双时间区分事实有效性与系统认知，来源契约和适用范围处理冲突，血缘连接所有派生知识。变更、权限收回和删除都必须传播到每种投影；快照发布则保证用户只看到经过验证的兼容状态。
