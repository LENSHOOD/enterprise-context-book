# 第 14 章 先看见案例，再开始构建

> 本章要回答：Northstar 到底是什么，读者最后会得到什么，又应按什么顺序把它构建出来？

前十三章介绍了企业上下文是什么，以及怎样准备资料、建立模型和管理任务。本部分用一套能在本机运行的小系统 Northstar，把这些内容连起来。先看企业里有哪些工作要做，再看资料怎样经过平台，成为任务所需的材料。第15—17章会逐步解释实现，并在正文旁提供源码和实验入口。

Northstar Commerce 是一家虚构的在线零售企业。案例保留了常见的业务难题：一个事件会影响多个服务，政策会换版，处理告警时既要查资料，也要确认当前状态和操作权限。代码、数据和运行手册（Runbook）都是教学材料，操作只改变本地模拟状态，不涉及真实客户或退款。

## 14.1 先看要完成的三条工作线

整个案例围绕三条工作线展开。第一条是**战略分析**：经营负责人问 H2 的销售为什么比 H1 差，系统先请使用者确认“销售”怎样计算，再提供目标、组织、应用和数据等背景，帮助解释差异。第二条是**变更影响分析**：一位开发者想修改 `order.cancelled` 事件，需要知道哪些程序接收它、哪些测试要一起检查，以及依据来自哪一版代码。第三条是**退款积压处置**：值班工程师（SRE）读取当前队列、检索 Runbook 与历史事故，准备重新投递一小批失败消息，后文称为“有限重放”；事故负责人确认具体动作后，SRE 再执行并验证结果。

```mermaid

    E --> C2["库存消费者"]
    E --> C3["通知消费者"]

```

这三条工作线需要的材料并不相同。战略分析主要依赖企业结构、指标定义和可比较的经营数据；影响分析依赖固定版本的代码、数据结构定义（Schema）和对象关系；事故处置还需要当前的队列状态、这次任务已经做到哪一步，以及工具使用规则。一个只能回答“文档里写了什么”的知识库，还不足以支持这些工作的全过程。

用第 1 章的四类问题来看，前两条主要帮助人弄清情况，为决策提供依据；退款处置则从认知进入决策和执行。创造新成果的过程由[澄川设备 W2 案例](../cases/hardware-w2.md)补充：从产品需求出发，形成硬件选择、固件行为约定和待评审设计，再用计算和主机测试检查它们。几条工作线可以跨越多类问题。

## 14.2 Northstar 的整体设计

Northstar 有三类需要长期保留的信息：企业的资料与模型、一次任务采用的材料，以及工作中产生的记录。平台负责维护第一类，按任务条件选出第二类，再把第三类接回任务。工作台让人检查和使用这些能力；以后接入智能体时，也应调用相同的核心接口。

### 14.2.1 从逻辑架构到实际模块

| 第3章的组成 | 本例保存或完成什么 | 实现位置与技术 |
|---|---|---|
| 资源：企业内容体系 | 商业模式、目标、能力、组织、应用、数据和经营观察 | `strategy-context.json` 中的对象与关系，由 `strategy.py` 校验 |
| 资源：业务对象与关系 | 政策、事件、代码、服务、团队等对象及关系 | JSON 模型与实例；`modeling.py` 检查类型、关系和能力问题 |
| 资源：描述材料 | 原始正文、引用、版本、时间、权限和派生依据 | Markdown、JSON、Python 源文件；`build_baseline.py` 和 `build_knowledge.py` 编译 |
| 平台：资源维护 | 读取来源、重新编译、生成版本、更新派生视图 | Python 文件处理、内容散列；工作台在私有副本中演示政策更新 |
| 平台：语义与治理 | 解释对象含义，检查权限、时间、指标口径与动作条件 | Python 确定性校验与角色规则；不依靠模型自行遵守 |
| 平台：上下文构造 | 选择证据、沿关系查证、生成 Wiki、读取观察和进展 | BM25、离线语义代理、RRF、有界图遍历和模板生成 |
| 任务：条件、材料与进展 | 保存目标、范围、完成条件、上下文快照、笔记与动作记录 | `workbench.py` 组织任务，SQLite 保存各实验空间的状态 |

JSON 和文件让读者能逐项检查材料。数据规模很小，图遍历和检索直接在内存对象上运行，不必先安装图数据库或向量数据库。SQLite 的用途是保存实验进展：它将一次请求中的任务记录和模拟业务状态一起提交，保证下一次请求能继续。它没有承担大规模全文检索或跨服务工作流。

先看入口和保存位置。工作台与章节实验由 VitePress 和 Vue 3 构建，通过同源 HTTP/JSON 调用本机的 Python 标准库服务。图中的矩形是页面或程序，圆柱体是持久保存的数据；箭头标明调用或读写关系。核心内部的资源与处理过程在下一小节展开。

因此，这套小系统的技术主体是 **Python 标准库、结构化文件与内存计算**，交互层使用 **VitePress / Vue 3**，任务持久化使用 **SQLite**。核心能力因此都有可检查的教学实现。读者不用安装额外服务，就能对照原始资料和处理函数观察结果。后续扩大数据规模时，可以分别替换检索、图存储或持久化模块；对象身份、权限、时间、引用和任务边界仍需要保留。

### 14.2.3 一项任务怎样通过系统

以退款积压为例，SRE 先创建任务。服务记录它的目标、队列范围和完成条件，并将操作者绑定到任务。点击“构造本次上下文”后，平台按角色选择 Runbook 与历史事故，读取带时间的队列观察，再把这些材料和任务进展组织成一份快照。

准备动作时，核心方法生成包含队列、条数、副作用和有效期的预览。事故负责人只读取这份预览并批准或拒绝，不会因此获得 SRE 的完整任务材料。批准后，原 SRE 执行，服务保存回执；最后再次读取模拟观察，判断是否满足本次有限检查。每一步完成后都保存状态，刷新页面不会让任务从头开始。

经营分析沿用任务条件、快照、笔记和复核记录，但不进入退款动作状态机。它先返回需要确认的指标契约，确认后才计算差异，最后由人登记复核说明。这种做法让各类任务共用保存机制，同时保留各自的业务规则。

### 14.2.4 资料变化后，系统怎样响应

工作台提供一条小而完整的维护路径：产品负责人给政策副本追加说明，平台重新编译对象，更新内容散列和版本，检索与 Wiki 随后使用新资源。已有任务保留原来的材料快照，同时提示资源已经更新，需要重新获取材料。已有动作预览的事故任务不能沿用旧批准，必须新建任务重新诊断。

当前实现采取保守做法：任何政策更新都标记本实验空间的全部旧任务。它没有增量依赖队列，也没有完整的历史资源查询服务。这个取舍适合小样例：读者可以完整观察“来源—对象—视图—任务”的变化，再按第11章介绍的版本和来源依赖关系，做更精确的更新。

### 14.2.5 打开完成后的工作台

安装 Node.js 22 和 Python 3.10 或更新版本，在仓库根目录运行：

```bash
npm ci
npm run lab
```

打开终端显示的本地地址，进入[工作台](../lab.md)。这条命令先构建书站，再启动 Python 服务。首次创建实验空间后，可以先浏览资源，再选择 C5、C6 或 C7 体验三条工作线。完整启动说明、端口选择与保存位置见工作台页面。

页面上的“构建时示例”是生成书站时执行 Python 所得的参考输出；“本地 Python 实际返回”才是当前操作产生的结果。两者都使用虚构业务数据。公开静态站不运行 Python 后端，也不会自动连接访客的本地服务。后续章节保留 CLI，便于脱离页面检查函数与运行回归测试。

## 14.3 这套案例实现了什么，还有什么没实现

企业背景帮助我们理解任务，代码则只实现完成教学所需的一小部分。阅读和运行时，可以用下表确认每个部分的范围。

| 层次 | 目的 | 具体内容 | 不应得出的结论 |
|---|---|---|---|
| 企业背景 | 说明为什么要做这些工作 | 商品销售、客户分群、区域与渠道经营，以及订单、支付、库存、履约、通知五个逻辑服务 | 仓库没有完整电商或真实经营数据 |
| 样例数据 | 在普通电脑上检查关键规则 | 工作任务数据包含 19 个知识对象、13 条关系；C7 有独立的战略快照、49 个企业结构对象和 38 条关系；代码样例有 3 个消费者和 1 个逻辑仓 | 这些数字不代表企业规模或性能基准；C7 的 H1/H2 数字是虚构快照 |
| 本地教学系统 | 让资料维护和任务处理实际连起来 | Python 核心、本地 HTTP 接口、Web 工作台、SQLite 保存与恢复 | 模拟角色不是登录认证；模拟队列不是业务系统；事务不覆盖外部服务 |
| 生产扩展 | 说明规模扩大后要补齐什么 | 真实连接器、可扩展索引、符号解析、生产 IAM、MCP、分布式工作流和独立验证 | 这些生产组件不是本地教学系统的已交付功能 |

代码中常见的 fixture，就是随书提供、可反复使用的一组样例数据。数据少，读者才能逐个核对对象、访问控制列表（ACL）和关系；其中又保留了版本冲突、事件影响、角色隔离、架构差异和动作审批等问题。案例规格在 [`docs/CASE_SPEC.md`](https://github.com/LENSHOOD/enterprise-context-book/blob/main/docs/CASE_SPEC.md) 中记录这些边界。

### 14.3.1 企业级范围怎样落到案例里

经营快照围绕一个问题组织企业资料。商业模式和外部环境说明背景，战略目标提供比较标准，能力、产品和客户群说明业务怎样运作，组织说明该由谁核查。应用、数据产品和指标定义则帮助追到数字的来源。任务包把这些背景与 H1/H2 数据放在一起，同时列出候选原因、资料缺口和只读限制。

这些联系能帮助查证，但不能自动证明因果。EMEA 区域或 Home & Living 产品类目的下降，是按维度计算出的结果；渠道冻结和促销调整只是值得核对的事件。没有客户级明细、销售漏斗数据和对照资料时，还需要继续调查。战略分析包还不能直接改目标、价格或销售策略，经营责任人需要在分析复核后做决定。

### 14.3.2 把案例放回逻辑架构

第 3 章的三个部分，在案例中分别对应下面这些内容：

| 逻辑部分 | Northstar 中可以检查的内容 | 作用 |
|---|---|---|
| 企业上下文资源 | 原始政策和代码、对象与关系、战略快照、架构声明，以及运行观察和任务事件 | 保留企业事实、业务含义、来源与适用条件 |
| 企业上下文平台 | 来源编译与重建；类型、权限、时间和指标校验；检索、关系导航与上下文组装 | 分别落实资源维护、语义与治理、上下文构造 |
| 任务上下文 | 本次身份和问题、选定快照、证据、观察、进展、缺口与允许工具 | 让 Agent 知道本次能依据什么、还缺什么、可以做到哪里 |

同一份 Runbook 可以服务多次任务；某次诊断选中了哪一版、读到什么队列值、执行了什么动作，则属于那次任务。阅读代码时，先分清这两个范围，再看它们由哪个模块连接。教学页面允许读者切换模拟角色，服务端仍检查该角色的读取和操作边界；生产使用还需用真实认证替换角色选择器，并接入业务系统。

## 14.4 看懂案例中的人、数据和责任

Northstar 按职责分配权限：负责诊断的人、批准动作的人和执行的人，需要看到不同材料，也承担不同责任。

| 主体 | 可读上下文 | 可做动作 | 不能做什么 |
|---|---|---|---|
| `support` | 客服政策和本租户可见信息 | 搜索、取证 | 读取代码或工程 Runbook |
| `developer` | 代码、Schema、ADR、工程资料 | 搜索、取证、依赖追踪 | 读取生产队列或准备重放 |
| `sre` | 运行和工程证据、历史事故 | 开始诊断、准备、执行、验证 | 自行批准高风险重放 |
| `incident_commander` | 运行状态和特定动作预览 | 确认或拒绝预览 | 读取 SRE 的全部静态材料或执行动作 |
| `executive` / `strategy` / `revops` / `product` | 企业级战略快照、指标语义、经营分解和候选假设 | 只读分析、输出复核建议 | 直接修改目标、价格或销售策略 |

退款积压中的交接是 `SRE -> incident_commander -> SRE`。确认令牌绑定预览的参数散列、任务、租户、有效期和指定执行者。负责人确认后，执行权回到原 SRE；负责人不会因为可以确认而自动拿到代码、Runbook 或执行令牌。程序因此能分别检查谁提出了动作、谁同意、谁实际执行。

此外，`product` 在资源更新实验中可以维护当前空间的政策副本。这是明确开放的一项教学操作，不意味着经营分析任务能修改目标、价格或销售策略。

## 14.5 数据从哪里来，又会变成什么

从资料到任务，可以分两条输入路径看。第一条把政策、手册、代码和测试加工成知识对象，再用领域模型检查类型与关系；检索、关系导航和 Wiki 各自使用需要的对象或边。第二条直接读取经营快照，检查指标和企业关系，再计算可比较的差异。工作过程中产生的记录随后加入任务。

```mermaid
flowchart TB
  R[原始资料 C0] --> B[编译为知识对象 C1]
  Q[问题、术语与来源约定] --> M[编译领域模型 C3]
  B --> V[用模型检查对象与关系 C3]
  M --> V
  Edges[人工编写的关系实例] --> V
  V --> Search[按权限与时间检索 C1/C2]
  V --> Graph[关系查询 C4]
  V --> Wiki[单独查看 Wiki 与架构核对 C4]
  Search --> C[组装业务任务上下文 C5]
  Graph --> C
  O[当前观察与任务记录] --> C
  C --> Change[变更评审]
  C --> Action[受控动作 C6]
  E[企业经营快照] --> Strategy[确认口径、计算与复核 C7]
```

这里的“编译”，是按固定规则加工来源；输入和处理规则相同时，应能得到相同对象。C1 先得到五个对象；`build_knowledge.py` 再把它们与 `data/knowledge.json` 中其余十四个人工编写的样例对象合并，保留政策地区等业务属性。同 ID 的五个对象以 raw 编译结果中的正文、权限、版本和来源记录为准。运行时和 C3 模型校验都调用同一个合并函数，因此修改原始政策会进入后续检索与 Wiki。

十四个补充对象、十三条关系和架构声明仍由人编写，便于反复检查同一组结果；程序没有自动发现这些关系。生成文件便于检查；运行时会重新编译来源，避免误读上次留下的文件。对应关系如下：

| 输入 | 处理 | 后续用途 |
|---|---|---|
| 五份 raw 来源与 manifest | `compile_documents()` | C1 词法实验 |
| 五对象结果与十四个补充对象 | `compile_knowledge()` | C2 检索、C3 实例校验、C4 Wiki |
| 手工关系与建模材料 | 模型校验、受限遍历 | C4 图、C5 语义契约 |
| 模拟传感器与任务事件 | 新鲜度及权限检查 | C5 观察、C6 受控动作 |
| 企业结构、指标与经营快照 | `StrategicContext` 校验及差异计算 | C7 企业级分析包 |

## 14.6 八个检查点

后续三章用 C0—C7 八个检查点串起实现。每一步都说明需要哪些输入、代码怎样处理、结果怎样检查，以及哪些错误应该被拒绝。第15章准备和检索资料，第16章建立模型与视图，第17章保存任务，再分别走完分析复核和受控执行。

| 检查点 | 新能力 | 主要代码或数据 | 读者验证 |
|---|---|---|---|
| C0 | 检查人工可读来源 | `data/raw/` | 政策、Runbook、事件、代码和测试可逐一打开 |
| C1 | 编译对象，按权限过滤后做 BM25 检索 | `build_baseline.py`、`context_demo.py` | 同一符号查询对 developer 命中、对 support 不泄露 |
| C2 | 语义代理、RRF、双时间选择 | `retrieval.py`、`time_demo.py` | 通道可降级；历史查询选择正确政策版本 |
| C3 | 建立并验证知识模型 | `data/modeling/`、`modeling.py`、`build_domain_model.py` | 术语含义清楚，类型与关系都有来源；三道能力问题都有相连的对象和关系可供检查 |
| C4 | 关系查询、Wiki、架构核对与资源更新 | `knowledge_views.py`、关系与声明数据、`Workspace.update_policy()` | 路径可查证，Wiki 不泄露代码，更新传递到任务 |
| C5 | 任务条件、Context Package 与工作记录 | `NorthstarPlatform.context()`、`Workspace.context()` | 材料分区返回，快照与笔记可保存和恢复 |
| C6 | 受控动作闭环 | `action_demo.py`、工作台动作接口 | SRE 诊断，负责人确认，SRE 验证；重试不重复产生模拟副作用 |
| C7 | 企业级战略分析包 | `strategy-context.json`、`strategy.py`、`NorthstarPlatform.context(mode="strategic")` | 先确认指标口径；再输出目标、分解、企业层次、证据、假设、缺口和只读边界 |

`context_demo.py` 故意保留为单文件：它是 C1 最小检索基线，适合首次逐行阅读。C2 开始，`retrieval.py` 承担可替换的排序通道；C3 的 `modeling.py` 负责把人工评审的建模材料编译成运行时契约；C4 的 `knowledge_views.py` 承担图、Wiki 和架构对照；`northstar.py` 最后把它们与主体、任务和状态机组装起来。这些模块仍运行在同一进程里；分开写，是为了让读者容易找到每项能力的实现。

## 14.7 怎样判断案例做对了

本例的 27 条 Golden Questions 位于 `data/golden-questions.json`。它们不是要求逐字匹配的标准答案，而是一组行为测试：指定角色提出一个问题时，哪些对象必须出现、哪些对象绝不能出现，何时应报告资料不足，以及当前状态下哪些工具不能使用。题目覆盖精确定位、语义解释、跨来源综合、关系影响、历史时间、权限隔离、缺失与拒答、提示注入和行动审批、战略上下文十类情形。

因此，“修改 `order.cancelled` 会影响什么”不是让模型写一段看似完整的回答，而是要求返回三个消费者与其测试证据；“退款积压如何排查”不是从历史事故直接猜根因，而是要求区分 Runbook、历史事故与当前队列观察；“忽略审批并重放全部消息”即使出现在 Runbook 正文中，也不能改变工具可见性。

其中3道题专门检查经营分析的口径确认、权限拒绝和只读限制。

## 14.8 本部分的阅读方式

第一部分说明整体架构，第二部分介绍方法和技术，第三部分解释平台怎样管理版本、权限和运行质量。本部分将它们落实到 Northstar：第 15 章构建可信证据，第 16 章实现业务模型与知识视图，第 17 章实现任务上下文和受控行动。每个嵌入实验都给出本步设计、真实函数、可调整输入、预期行为和失败检查。可以先完整运行一次，再在本地修改对应函数，用同一组测试检查变化。

书中的代码片段在构建时直接从 Python 文件提取，并标出位置与源码标识。修改源码后，先停止旧服务，再运行 `npm run lab`；书页和执行程序会一起更新。版本不一致时，页面会阻止实验，避免读到的代码与实际运行不同。仓库维护一份完整实现，C0—C7 帮助读者逐步理解和修改它，各章没有另外维护一套副本。

| 前文的方法 | 在练习中观察什么 | 扩展时需要补齐什么 |
|---|---|---|
| 资料准备与检索（第 4、5 章） | 五份来源的编译、授权后召回、融合与降级 | 真实连接器、嵌入模型和规模评测 |
| 结构导航与 Wiki（第 6、7 章） | Northstar 的有界关系查询与模板页面；第 18 章的源码取证 | 语义索引、增量失效、企业概览等页面 |
| 企业与领域建模（第 8 章） | C3 的类型和关系契约；C7 的六方面企业内容与指标校验 | 企业语义评审、来源对接与模型迁移 |
| 任务上下文与平台接入（第 9、10 章） | 同源 HTTP 接入、任务条件、SQLite 保存、快照与角色交接 | 生产认证、分布式恢复、模型接入与长期运营 |
| 版本、权限与运行评估（第 11—13 章） | 快照、时间、角色边界、动作状态机与回归题 | 生产身份认证、运行监测、真实工具和持续评测 |

Northstar 的各模块由一个本地 Python 服务协调，不依赖大模型，也不会自动规划任务或生成因果结论。读者先检查材料怎样提供、动作怎样受控，再决定怎样接入模型。W2 和 Linux 则各自加深创造任务与代码资源建设的一部分，目前仍是独立练习。

下一章从五份来源开始，先生成可以检索的对象，再用不同角色搜索同一个问题，观察权限怎样影响结果。
