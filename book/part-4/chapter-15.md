# 第 15 章 从来源到可信检索

> 本章要回答：企业中的文档、代码和规则怎样变成可检索的证据，并在版本、权限和时间都正确的前提下回答问题？

上一章介绍了三条工作线：经营负责人比较 H1/H2 销售，开发者检查事件变更的影响，SRE 排查退款积压。要回答这些问题，先得拿对材料：销售按什么口径计算，代码是哪一版，用户有权看什么，政策在当时是否有效。即使一段文字看起来很相关，这些条件不对，也不能直接用来回答。

本章先把来源加工成带身份、版本、权限和时间的对象，再为搜索建立索引。收到问题后，系统按任务和用户身份选材料、计算排名，并保留原文引用。这些加工结果都应能够从来源重新生成，方便更新和核查。

本章将第 4、5 章的资料准备与检索方法，以及第 11、12 章的版本和权限规则，落实到 Northstar 的 C0、C1、C2。每一步先解释要解决的问题，再在正文中查看真实函数和运行结果。在本地书站中，实验直接调用 Python；公开书站保留可展开的代码和构建时示例。启动方法见[工作台](../lab.md)。

## 15.1 先说清楚什么样的结果才算可信

传统站内搜索通常把“相关不相关”作为主要目标。企业上下文至少还要同时满足五项约束：

| 约束 | 需要回答的问题 | Northstar 中的例子 |
|---|---|---|
| 身份 | 这条材料在企业中代表什么对象？ | `order.cancelled v2` 是事件 Schema，不是一段普通 JSON |
| 版本 | 结论基于哪个不可变版本？ | 教学代码用 `commit:abc123` 演示版本坐标，来源内容另有散列 |
| 权限 | 当前使用者是否有权使用这个对象？ | support 的候选集合中不应出现代码对象 |
| 时间 | 问的是当时有效的规则，还是平台当时已知的规则？ | 7 月政策与 8 月政策必须分开 |
| 证据 | 结果能否定位到来源，并说明怎样加工而来？ | 命中包含 `citation`、版本、通道和权威等级 |

相关性只在这些边界内才有意义。一段材料即使相关，用户无权使用、时间不适用或来源无法核查时，也不能直接作为答案依据。

这也解释了为什么 Northstar 从五份很小的来源开始。小规模让读者可以人工核对每一个对象；真正要验证的不是吞吐量，而是上述五项要求是否从读取来源一直保持到返回证据。

`abc123` 是虚构的版本标记，`code://northstar/...` 也是教学引用格式。本例可以核对本地来源、提取结果和内容散列，但不能用这个标记检出一个真实提交。第 18 章的 Linux 练习会进一步验证真实 Git 提交与源码坐标。

## 15.2 文档、代码和规则不能用同一种方式切块

Northstar 的原始材料包括政策、运行手册、事件 Schema、代码和测试。它们都可以保存为文件，但不能因此使用同一种解析方式。

- 政策的语义依赖标题、条款、生效区间和发布状态；
- Runbook 的语义依赖前置条件、操作步骤、风险和验证方法；
- Schema 的字段、版本和兼容性比自然语言摘要更重要；
- 代码的边界通常是文件、类型、函数和符号，而不是固定长度字符；
- 测试除了文本，还表达“哪个行为由什么断言保护”。

若对它们统一按 800 个字符切块，系统会得到形状相似、意义不同的文本碎片。函数可能在签名与函数体之间断开，政策例外可能脱离适用范围，测试名称也可能与断言分离。向量化不会修复这些损失，无法把这些被切断的含义补回来。

因此，接入资料时要先确定**什么内容算一个完整对象**，再决定**搜索结果应该返回多大一段**。Northstar 的代码来源清单不是说“读取这个文件”，而是明确提取 `handle_order_cancelled`：

```json
{
  "id": "code-refund-consumer",
  "path": "code/refund-worker/consumer.py",
  "parser": "python_symbol",
  "symbol": "handle_order_cancelled",
  "acl": ["developer"],
  "citation": "code://northstar/refund-worker@abc123/consumer.py#handle_order_cancelled"
}
```

这里同时出现了来源坐标、逻辑对象和访问边界。本例用 Python AST 提取函数正文。扩展到其他语言时，可以用 Tree-sitter 提取语法结构，再由语言索引器或编译器补充符号解析；SCIP 是交换这类索引的格式，LSP 则提供在线导航接口。第 6 章解释了它们的分工。换用这些工具后，来源坐标、对象身份和访问边界仍要保留。

## 15.3 在原始来源和搜索索引之间，加一层稳定对象

直接让全文索引、向量库和图数据库各自读取来源，会迅速产生三套对象 ID、三套删除处理规则和三种更新时间。Northstar 在来源与索引之间加入统一知识对象，各类索引和视图都引用统一的对象版本。

一个对象可以分成四组信息来读：

| 层 | 典型字段 | 作用 |
|---|---|---|
| 身份 | `id`、`entity_type`、`tenant` | 识别同一逻辑对象，并划定租户 |
| 内容 | `text`、结构化字段、`content_hash` | 保存可检索内容并检测变化 |
| 使用规则 | `acl`、`authority`、`time` | 决定谁能用、应信到什么程度、何时有效 |
| 可追溯性 | `source`、`citation`、`lineage` | 回到原始版本并解释派生过程 |

`build_baseline.py` 将这些约定落实到 `compile_documents()`。先在下面的代码选择框查看 `parse_source()`，理解不同格式怎样形成正文；再选择 `compile_documents()`，沿着“读取来源清单—检查身份与路径—解析正文—计算散列—返回对象”读一遍。最后执行资源实验，对照代码检查生成字段。

这里展示的是平台合并后的可见资源，不只包含最初五份来源。亲手构建时，先用本章末尾的 `build_baseline.py` 生成五个对象，再用 `build_knowledge.py` 合并其余十四个补充对象。经营快照则沿独立的结构化校验路径进入系统；选择经营负责人查看资源目录，可以看到它的企业对象。

`id` 说明“这是谁”，`version` 和内容散列区分“这是哪一版”，`citation` 帮助人找到来源，`lineage` 记录加工过程。它们各有用途：URL 可能指向已经更新的页面，散列虽然能检查内容是否变化，却不能单独告诉人去哪里找原文。

### 为什么这里使用“编译”这个词

这里说“编译”，是为了强调三件事。第一，系统清楚知道输入是什么、输出是什么。第二，只要输入和编译器版本相同，结果就应相同。第三，输出只是加工结果，可以删除后重新生成。因此，索引损坏时能够重建，解析器升级时可以比较新旧结果，来源撤销时也能找到所有受影响的派生对象。

以后更换数据库或搜索引擎时，也应保留这套对象定义。这样，索引可以重建，来源、版本和权限仍能对得上。

## 15.4 先按权限缩小候选范围，再计算相关性

Northstar 用对象中的 ACL 列表记录允许读取的角色。developer 能看代码，support 不能。查询顺序是：

```python
allowed = [doc for doc in documents if role in doc["acl"]]
hits = bm25(question, allowed)
```

这两行表达了一个比代码本身更重要的原则：**先确定当前用户有权使用哪些对象，再对这些对象计算相关性。**

若先从全局索引取 Top-K，再删除无权结果，会出现三类问题：

1. 无权对象占据了前 K 个结果的名额，把本来能用的材料挤了出去；
2. 分数、数量、延迟或错误差异可能泄露无权对象存在；
3. 其他检索通道的合并、重排或关系查询可能已经用到了无权材料。

生产系统不一定把 ACL 数组复制到每个索引。也可以根据用户属性生成数据库过滤条件，按权限范围分开建立索引，或由权限服务返回允许读取的对象版本。无论怎样实现，每条检索通道都要检查同样的访问规则，缓存也必须区分使用者、租户和权限规则版本。授权服务不可用时应关闭访问，而不是退化成全局检索。

“无权”与“确实不存在”对调用者通常应给出相同的外部表现。审计系统可以记录策略拒绝，但面向用户的错误不应通过对象名称或计数帮助其枚举另一个安全域。

下面把这条规则落实到一次可见对比。先让开发者搜索函数名，再把角色切到客服，保持问题相同。注意 `search()` 先调用 `current_documents()`，然后才计算分数。换角色应改变进入排序的对象集合，而不只是改变卡片的显示方式。

## 15.5 为什么不是只用一种检索

企业问题的表达方式不同，单一通道很难兼顾。Northstar 的几条工作线已经包含四种查询：

| 查询 | 最有用的能力 | 原因 |
|---|---|---|
| `handle_order_cancelled` 在哪里 | BM25 或符号索引 | 精确标识符不需要语义猜测 |
| “退款失败后怎么办” | 语义召回与 Wiki | 用户措辞可能与 Runbook 不同 |
| 修改事件会影响谁 | 图遍历 | 目标是关系路径，不是相似文本 |
| H2 的销售为什么低于 H1 | 指标语义、结构化数据与企业架构路径 | 目标是可比较事实和待验证假设，不是相似段落 |

BM25 对函数名、错误码、合同术语和产品编号仍然非常重要。语义检索用于跨越同义表达和自然语言改写。图适合依赖、所有权和影响路径。层级 Wiki 则帮助查询先到系统或主题，再下钻到来源。第 5 章已经给出混合检索原理，本章关心它们怎样共享同一对象和安全边界。

Northstar 的 C2 用同义词扩展加词集合重合度（Jaccard 相似度），模拟第二条排序通道，称为“离线语义代理”。这样，读者可以专注于检查两路结果怎样合并、故障时怎样继续、结果怎样标出来源。这个简单算法不能代表真实嵌入模型的搜索质量。

### 用 RRF 合并两条通道的排名

BM25 分数、余弦相似度和图距离不是同一种量，直接相加很难解释。倒数排名融合（Reciprocal Rank Fusion，RRF）只使用各通道中的名次：

$$
\operatorname{RRF}(d)=\sum_{r\in R}\frac{1}{k+\operatorname{rank}_r(d)}
$$

一个对象同时被词法和语义通道排到前列时，会得到更高融合分；只被一个通道发现的对象仍可保留。Northstar 同时返回贡献通道，因此读者能区分“精确命中”和“仅由语义代理召回”。RRF 的经典研究说明了这种融合方法的经验效果，但参数和候选数量仍需用企业自己的问题集验证。[Cormack 等，Reciprocal Rank Fusion](https://dl.acm.org/doi/10.1145/1571941.1572114)

RRF 不会判断来源是否权威，不会解决重复内容，也不会替系统选择正确时间版本。合并前仍要检查权限和范围；合并后还要核对来源、去掉重复对象，并按时间和任务需要选择材料。

## 15.6 不是每个问题都要把所有检索方式跑一遍

成熟的检索系统不会对每个问题都固定运行 BM25、向量、图和重排。查询规划器做的事情，可以概括为“先判断这道题应该怎么查”。它至少要识别四件事：

- 本次要交付解释、影响范围、设计成果，还是动作结果；
- 哪些资源能支持这个结果，例如政策、代码关系、经营数据或实时观察；
- 查询中的实体、版本、时间、业务范围与访问身份是什么；
- 哪些方式能在允许的耗时和成本内，提供足够新的材料。

对精确符号查询，BM25 和符号索引可能已经足够；对影响分析，先定位事件，再沿允许边扩展；对退款队列“现在有多少条”，静态索引不应作答，而应调用受限实时工具。每次都运行所有通道，会增加成本、重复材料和需要保护的接口，也可能让查询更慢。

Northstar 没有实现完整查询规划器。读者通过命令参数指定关系查询的起点和需要读取的运行资源，这些参数展示了规划器将来需要给出什么。生产中的模型可以提出计划，但执行程序仍应检查输入格式、允许关系、结果数量、跳数和超时，不能直接运行任意搜索表达式。

战略问题的规划路径也不同。系统先把“销售”解析为一个待确认的指标，而不是直接把问题向量化；确认指标定义、半年度边界、实际/目标场景和快照后，才读取战略目标、业务能力、组织、应用、数据产品与经营观察。若口径没有确认，上下文包应停在 `needs_clarification`，不生成差异和原因。这样可以防止模型把收入、订单额和回款混成同一个“销售”。

C7 的四十九个对象保留在 `strategy-context.json` 中，由 `StrategicContext` 直接校验和计算。它们没有先被编译成上述十九个知识对象，也不经过 BM25 排名。这里使用第5、8章介绍的另一种取证方式：对已有结构的数据，按明确口径查询与计算，保留字段来源和关系。

## 15.7 一个 `updated_at` 说不清历史

假设旧政策 7 月有效，新政策 8 月生效，但平台直到8月底才收录。下面两个问题答案不同：

1. 7 月 20 日业务上适用哪条政策？
2. 平台在 7 月 20 日当时知道哪条政策？

前者由业务有效时间决定，后者由系统观察时间决定。Northstar 为对象保留 `valid_from` / `valid_to` 与 `observed_at` 两条时间轴。历史业务解释使用第一条；审计“当时的智能体为何这样回答”还需要第二条以及当时的资源版本清单（Snapshot Manifest）。

这里的知识对象沿用字段名 `observed_at` 表示平台首次记录时间，对应第 11 章的 `recorded_at`。实时队列中的同名字段则表示采样时间。阅读接口时要结合对象类型解释：前者回答平台何时知道，后者回答状态何时测得。

若查询的是平台收录之前的时刻，Northstar 的双时间接口返回空集合。这不是系统失败，而是诚实表达“平台当时不知道”。在线默认检索也使用当前教学时钟过滤失效政策；历史问题必须显式传入 `valid_at` 和 `observed_at`，不能把历史题和当前题混在同一个默认列表里。用今天已经补齐的材料回答过去，再声称这是历史重放，会制造虚假的确定性。

这组样例只保存首次记录时间，因此不能还原每次索引修改。生产系统还需保存来源水位、对象版本、解析器版本、索引快照和删除事件。第 11 章进一步讨论双时间与快照发布。

## 15.8 部分能力不可用时，怎样继续

系统出故障时还能提供什么，同样需要设计。Northstar 用“关闭语义代理”模拟少一条检索通道的情形：BM25 继续搜索已授权对象，结果在 `degraded_channels` 中标出停用通道。本例没有连接真实语义服务，也没有实现远程故障的自动检测。

要不要继续、还能返回什么，取决于故障发生在哪里：

| 故障 | 可以做什么 | 不应做什么 |
|---|---|---|
| 向量通道不可用 | 退化到授权后的 BM25，并标注召回能力下降 | 绕过 ACL 或隐藏降级事实 |
| 图快照落后 | 返回文本证据，标记影响路径可能不完整 | 把缺失边解释成“没有影响” |
| 权限服务不可用 | 关闭受保护对象访问 | 使用上一次用户的权限缓存 |
| 实时资源超时 | 返回静态诊断知识并列出 `missing` | 用历史事故数值冒充当前状态 |
| 引用无法解析 | 降低或拒绝使用该证据 | 只保留摘要并删除来源坐标 |

这些处理规则说明：材料不完整时，系统还能提供哪些帮助，哪些判断必须暂停。

现在将第二条排序通道和时间条件一起接入。在下面先关闭语义代理，只看 BM25；再打开代理，观察命中的通道标记；最后关闭两条通道，确认平台如实返回空证据。历史时间输入接受带时区的 ISO 时间，例如 `2026-07-20T12:00:00Z`。源码中的 `documents_as_of()` 负责选择版本，RRF 只处理已经通过过滤的名次。

检查五个结果：同一输入能重新生成相同对象；developer 能搜到代码而 support 不能；关闭语义通道后，结果说明哪项能力不可用；历史查询使用正确的政策时间；经营题先确认口径，再给出总额、分解和企业背景。

### 从教学实现走向生产

本例分别演示了对象加工、两路排序和权限检查，但没有验证连接器覆盖率、真实语义搜索质量或大数据性能。替换为生产组件时，要保留以下约定：

- 对象版本可以追到来源，索引和视图可以从相应来源重新生成；
- 生产全文、向量、图和 Wiki 应引用统一 `version_id`；本例以对象版本、内容散列和引用表达该约束；
- 授权在每条召回通道之前执行；
- 查询返回来源、版本、时间、权威等级和通道信息；
- 快照与降级状态对调用方可见；
- 新增通道后，要用评测集里对应的任务检查是否确实改善了结果。

PostgreSQL 全文检索、pgvector、Elasticsearch 或专用向量数据库都可以保存和查询这些索引。选择它们的依据应是数据规模、过滤能力、更新模式、运维成熟度和评测结果，而不是把某个产品名当作架构本身。[PostgreSQL 全文检索](https://www.postgresql.org/docs/current/textsearch.html) [pgvector](https://github.com/pgvector/pgvector)

## 本章小结

可信检索从读懂来源开始。不同资料保留自己的结构，编译后的对象带上身份、版本、权限、时间和加工记录。收到问题后，系统先按权限和任务缩小范围，再计算相关性，并让证据能够回到原文。通过 C0—C2，读者已经能检查从来源到结果的主要处理步骤。下一章将从工作问题设计模型，再用模型校验具体对象和关系，生成用于查证、阅读与架构核对的视图，并观察来源变化怎样传到这些视图。
