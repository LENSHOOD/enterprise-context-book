# 第 15 章 从来源到可信检索

> 本章要回答：企业中的文档、代码和规则怎样变成可检索的证据，并在版本、权限和时间都正确的前提下回答问题？

上一章展示了 Northstar 的三类任务。经营负责人问“为什么 H2 的销售比 H1 差”，开发者问“修改 `order.cancelled` 会影响什么”，SRE 问“退款为什么积压”。表面看，这些问题都可以交给搜索框；实际上，它们要求系统先回答一组更基础的问题：指标和搜索的口径是什么，搜索的是哪一版材料，查询者有权看到什么，结果来自原文还是派生摘要，政策在什么时候有效，以及某条检索通道故障时还能相信什么。

因此，可信检索不是“把文件切块后放进向量库”。它是一套可以重复运行、也可以从头重建的加工流程：原始来源是事实依据；知识对象给来源加上身份、版本、权限和时间；索引只是为了搜索而生成的视图；收到问题后，系统再根据任务和用户身份选择合适的索引，合并候选材料，并返回能够跳回原文的证据。

本章先讲清这条链的设计，再在最后把设计映射到 Northstar 的 C0、C1、C2 三个实现检查点。

## 15.1 先说清楚什么样的结果才算可信

传统站内搜索通常把“相关不相关”作为主要目标。企业上下文至少还要同时满足五项约束：

| 约束 | 需要回答的问题 | Northstar 中的例子 |
|---|---|---|
| 身份 | 这条材料在企业中代表什么对象？ | `order.cancelled v2` 是事件 Schema，不是一段普通 JSON |
| 版本 | 结论基于哪个不可变版本？ | 代码引用固定到 `commit:abc123` |
| 权限 | 当前主体是否有权让该对象参与计算？ | support 不应进入代码对象的候选集合 |
| 时间 | 问的是当时有效的规则，还是平台当时已知的规则？ | 7 月政策与 8 月政策必须分开 |
| 证据 | 结果能否回到来源坐标，并说明经过了什么派生？ | 命中包含 `citation`、版本、通道和权威等级 |

相关性只在这些边界内才有意义。一个高度相关但无权、过期或无法回跳的片段，不是“稍差的结果”，而是不应进入答案的结果。

这也解释了为什么 Northstar 从五份很小的来源开始。小规模让读者可以人工核对每一个对象；真正要验证的不是吞吐量，而是上述五个不变量是否从摄取一直保持到回答。

## 15.2 文档、代码和规则不能用同一种方式切块

Northstar 的原始材料包括政策、运行手册、事件 Schema、代码和测试。它们都可以保存为文件，但不能因此使用同一种解析方式。

- 政策的语义依赖标题、条款、生效区间和发布状态；
- Runbook 的语义依赖前置条件、操作步骤、风险和验证方法；
- Schema 的字段、版本和兼容性比自然语言摘要更重要；
- 代码的边界通常是文件、类型、函数和符号，而不是固定长度字符；
- 测试除了文本，还表达“哪个行为由什么断言保护”。

若对它们统一按 800 个字符切块，系统会得到形状相似、意义不同的文本碎片。函数可能在签名与函数体之间断开，政策例外可能脱离适用范围，测试名称也可能与断言分离。向量化不会修复这些损失，只会让损坏后的片段更容易被找到。

因此，接入资料时要先确定**什么内容算一个完整对象**，再决定**搜索结果应该返回多大一段**。Northstar 的代码来源清单不是说“读取这个文件”，而是明确提取 `handle_order_cancelled`：

```json
{
  "id": "code-refund-consumer",
  "path": "code/refund-worker/consumer.py",
  "parser": "python_symbol",
  "symbol": "handle_order_cancelled",
  "acl": ["developer"],
  "citation": "code://northstar/refund-worker@abc123/consumer.py#handle_order_cancelled"
}
```

这里同时出现了来源坐标、逻辑对象和访问边界。真实代码平台可以用 Tree-sitter、SCIP 或编译器索引替代教学解析器，但替换后仍应得到这三类信息，而不是只生成一段函数摘要。

## 15.3 在原始来源和搜索索引之间，加一层稳定对象

直接让全文索引、向量库和图数据库各自读取来源，会迅速产生三套对象 ID、三套删除语义和三种更新时间。Northstar 在来源与索引之间加入统一知识对象，所有投影只引用对象版本。

一个对象可以拆成四层理解：

| 层 | 典型字段 | 作用 |
|---|---|---|
| 身份 | `id`、`entity_type`、`tenant` | 识别同一逻辑对象，并划定租户 |
| 内容 | `text`、结构化字段、`content_hash` | 保存可检索内容并检测变化 |
| 治理信封 | `acl`、`authority`、`time` | 决定谁能用、应信到什么程度、何时有效 |
| 可追溯性 | `source`、`citation`、`lineage` | 回到原始版本并解释派生过程 |

`build_baseline.py` 所做的关键工作不是“把 Markdown 转成 JSON”，而是编译这层稳定契约：

```python
text = parse_source(source_path, item["parser"], item.get("symbol"))
source_uri = f"fixture://northstar/{item['path']}@{item['version']}"
content_hash = f"sha256:{hashlib.sha256(text.encode()).hexdigest()}"

document = {
    "id": item["id"],
    "version": item["version"],
    "citation": item["citation"],
    "acl": item["acl"],
    "source": {"uri": source_uri, "revision": item["version"]},
    "time": {"valid_from": ..., "observed_at": ...},
    "lineage": {"derived_from": [source_uri], "transform": "baseline-compiler@1"},
}
```

逻辑 `id` 用于把不同版本认作同一对象；`version` 和内容散列区分不可变状态；`citation` 面向使用者回跳；`lineage` 面向系统解释这个对象怎样生成。四者不能互相替代。只保存 URL 无法证明内容版本，只保存散列又无法让人定位来源。

### 为什么这里使用“编译”这个词

这里说“编译”，是为了强调三件事。第一，系统清楚知道输入是什么、输出是什么。第二，只要输入和编译器版本相同，结果就应相同。第三，输出只是加工结果，可以删除后重新生成。因此，索引损坏时能够重建，解析器升级时可以比较新旧结果，来源撤销时也能找到所有受影响的派生对象。

这与“把所有内容永久导入一个向量数据库”有本质区别。数据库是投影的实现，知识对象契约才是系统可以长期演进的接口。

## 15.4 先按权限缩小候选范围，再计算相关性

Northstar 采用最容易看清的角色 ACL。developer 能看代码，support 不能。查询顺序是：

```python
allowed = [doc for doc in documents if role in doc["acl"]]
hits = bm25(question, allowed)
```

这两行表达了一个比代码本身更重要的原则：**先确定当前用户有权使用哪些对象，再对这些对象计算相关性。**

若先从全局索引取 Top-K，再删除无权结果，会出现三类问题：

1. 无权对象占据候选名额，导致用户本来有权看到的材料没有进入 Top-K；
2. 分数、数量、延迟或错误差异可能泄露无权对象存在；
3. 后续的向量融合、重排和图扩展已经接触了不该参与计算的内容。

生产系统不一定把 ACL 数组复制到每个索引。它可以把主体属性编译为数据库过滤条件，按安全域建立分区索引，或由策略服务返回可用对象版本集合。但每一条通道都要执行等价约束，缓存键也必须包含主体、租户和策略版本。授权服务不可用时应关闭访问，而不是退化成全局检索。

“无权”与“确实不存在”对调用者通常应给出相同的外部表现。审计系统可以记录策略拒绝，但面向用户的错误不应通过对象名称或计数帮助其枚举另一个安全域。

## 15.5 为什么不是只用一种检索

企业问题的表达方式不同，单一通道很难兼顾。Northstar 的三类任务已经包含四种查询：

| 查询 | 最有用的能力 | 原因 |
|---|---|---|
| `handle_order_cancelled` 在哪里 | BM25 或符号索引 | 精确标识符不需要语义猜测 |
| “退款失败后怎么办” | 语义召回与 Wiki | 用户措辞可能与 Runbook 不同 |
| 修改事件会影响谁 | 图遍历 | 目标是关系路径，不是相似文本 |
| H2 的销售为什么低于 H1 | 指标语义、结构化数据与企业架构路径 | 目标是可比较事实和待验证假设，不是相似段落 |

BM25 对函数名、错误码、合同术语和产品编号仍然非常重要。语义检索用于跨越同义表达和自然语言改写。图适合依赖、所有权和影响路径。层级 Wiki 则帮助查询先到系统或主题，再下钻到来源。第 5 章已经给出混合检索原理，本章关心它们怎样共享同一对象和安全边界。

Northstar 的 C2 没有引入真实嵌入模型，而是使用同义词扩展加 Jaccard 相似度作为“离线语义代理”。这样做不是因为它足够好，而是为了把实验变量限制为：第二条排序通道加入后，融合、降级和来源标记是否正确。它的质量不能外推到生产语义搜索。

### RRF 只负责合并排名，不负责判断证据真假

BM25 分数、余弦相似度和图距离不是同一种量，直接相加没有稳定含义。倒数排名融合（Reciprocal Rank Fusion，RRF）只使用各通道中的名次：

$$
\operatorname{RRF}(d)=\sum_{r\in R}\frac{1}{k+\operatorname{rank}_r(d)}
$$

一个对象同时被词法和语义通道排到前列时，会得到更高融合分；只被一个通道发现的对象仍可保留。Northstar 同时返回贡献通道，因此读者能区分“精确命中”和“仅由语义代理召回”。RRF 的经典研究说明了这种融合方法的经验效果，但常数和候选规模仍应由企业题集验证。[Cormack 等，Reciprocal Rank Fusion](https://dl.acm.org/doi/10.1145/1571941.1572114)

RRF 不会判断来源是否权威，不会解决重复内容，也不会替系统选择正确时间版本。融合前仍要做权限和范围过滤，融合后还要按规范来源、对象去重、时间和任务预算组装证据。

## 15.6 不是每个问题都要把所有检索方式跑一遍

成熟的检索系统不会对每个问题都固定运行 BM25、向量、图和重排。查询规划器做的事情，可以概括为“先判断这道题应该怎么查”。它至少要识别四件事：

- 任务属于政策解释、代码定位、影响分析还是实时诊断；
- 任务属于战略分析、变更影响还是执行处置；
- 查询中是否包含实体、版本、时间或精确标识符；
- 哪些来源类型和安全域与任务有关；
- 哪些通道的成本和新鲜度满足当前 SLO。

对精确符号查询，BM25 和符号索引可能已经足够；对影响分析，先定位事件，再沿允许边扩展；对退款队列“现在有多少条”，静态索引不应作答，而应调用受限实时工具。所有通道并发看似能力最强，实际会增加延迟、成本、重复证据和攻击面。

Northstar 没有实现完整查询规划器。它通过命令参数显式选择图种子和运行资源，让读者能看见未来规划器应产生的结构化计划。生产中的模型可以提出计划，但执行层只接受受限 Schema、边类型、候选数、跳数和超时，不能执行任意搜索表达式。

战略问题的规划路径也不同。系统先把“销售”解析为一个待确认的指标，而不是直接把问题向量化；确认指标定义、半年度边界、实际/目标场景和快照后，才读取战略目标、业务能力、组织、应用、数据产品与经营观察。若口径没有确认，Context Package 应停在 `needs_clarification`，不生成差异和原因。这样可以防止模型把收入、订单额和回款混成同一个“销售”。

## 15.7 一个 `updated_at` 说不清历史

假设旧政策 7 月有效，新政策 8 月生效，但平台直到 8 月底才完成摄取。下面两个问题答案不同：

1. 7 月 20 日业务上适用哪条政策？
2. 平台在 7 月 20 日当时知道哪条政策？

前者由业务有效时间决定，后者由系统观察时间决定。Northstar 为对象保留 `valid_from` / `valid_to` 与 `observed_at` 两条时间轴。历史业务解释使用第一条；审计“当时的智能体为何这样回答”还需要第二条以及当时发布的 Snapshot Manifest。

若查询时间早于摄取时间，Northstar 的双时间接口返回空集合。这不是系统失败，而是诚实表达“平台当时不知道”。在线默认检索也使用当前 fixture 时钟过滤失效政策；历史问题必须显式传入 `valid_at` 和 `observed_at`，不能把历史题和当前题混在同一个默认列表里。用今天已经补齐的材料回答过去，再声称这是历史重放，会制造虚假的确定性。

教学 fixture 只保存首次观察时间，因此不能还原每次索引修改。生产系统还需保存来源水位、对象版本、解析器版本、索引快照和删除事件。第 11 章进一步讨论双时间与快照发布。

## 15.8 失败时应怎样退化

系统出故障时怎样回答，同样决定了检索是否可信。语义服务不可用时，Northstar 仍可在已授权对象上运行 BM25，同时在 `degraded_channels` 中明确说明语义通道不可用。它不会把能力缩水后的结果伪装成完整答案。

不同故障的安全策略并不相同：

| 故障 | 可以做什么 | 不应做什么 |
|---|---|---|
| 向量通道不可用 | 退化到授权后的 BM25，并标注召回能力下降 | 绕过 ACL 或隐藏降级事实 |
| 图快照落后 | 返回文本证据，标记影响路径可能不完整 | 把缺失边解释成“没有影响” |
| 权限服务不可用 | 关闭受保护对象访问 | 使用上一次用户的权限缓存 |
| 实时资源超时 | 返回静态诊断知识并列出 `missing` | 用历史事故数值冒充当前状态 |
| 引用无法解析 | 降低或拒绝使用该证据 | 只保留摘要并删除来源坐标 |

这张表比“系统有备用模型”更重要，因为它定义了在不完整条件下还允许做出什么声明。

## 15.9 把设计映射到 Northstar 的实现

先看一个实际变化怎样走完整条链。运行 `python3 src/tutorial_experiments.py change`，脚本会在临时目录复制数据，把一个检索标记加入原始政策，再重新启动平台。你应看到快照 ID 改变，政策被检索命中，Wiki 也出现新内容；仓库里的原始资料不会被改动。把标记换成你自己的条款并重跑，可以检查自己是否真正理解来源、对象和视图之间的关系。

理解设计后，再运行 C0–C2。操作集中在这一节，避免打断前面的推理。

```bash
cd examples/enterprise-case

# C0：人工检查来源及清单。
find data/raw -type f | sort

# C1：编译五个代表性对象，并比较不同角色的候选集合。
python3 src/build_baseline.py
# 合并五个编译对象与十四个补充对象，供完整案例检查。
python3 src/build_knowledge.py
python3 src/context_demo.py \
  "handle_order_cancelled create_refund" \
  --role developer \
  --data generated/baseline-knowledge.json
python3 src/context_demo.py \
  "handle_order_cancelled create_refund" \
  --role support \
  --data generated/baseline-knowledge.json

# C2：观察业务时间与系统观察时间的差异。
python3 src/time_demo.py

# C7：战略路径先返回待确认的指标契约，再在确认后生成企业级分析包。
python3 src/strategy_demo.py "H2 的销售情况为什么比 H1 差这么多？"
python3 src/strategy_demo.py "H2 的销售情况为什么比 H1 差这么多？" \
  --confirm-definition

# 验证编译确定性、ACL-first、融合降级和双时间行为。
python3 -m unittest tests.test_build_baseline tests.test_northstar -v
```

预期结果不是某段固定自然语言，而是五个行为：同一输入可确定性重建；developer 能命中代码而 support 不能；语义通道停用时结果明确标注降级；历史查询选择与业务时间和观察时间一致的政策版本；战略题在口径未确认时拒绝直接计算，确认后才返回总额、分解和企业层次。

### 从教学实现走向生产

Northstar 的五对象编译器只证明对象契约，不代表连接器覆盖；离线语义代理只证明多通道编排，不代表语义质量；内存列表只证明查询顺序，不代表规模性能。生产替换时应保持以下接口不变：

- 来源可以重新生成对象版本，派生投影可以删除重建；
- 生产全文、向量、图和 Wiki 应引用统一 `version_id`；本例以对象版本、内容散列和引用表达该约束；
- 授权在每条召回通道之前执行；
- 查询返回来源、版本、时间、权威等级和通道信息；
- 快照与降级状态对调用方可见；
- 新增通道必须在 Golden Dataset 的特定任务分桶中证明收益。

PostgreSQL 全文检索、pgvector、Elasticsearch 或专用向量数据库都可以成为投影后端。选择它们的依据应是数据规模、过滤能力、更新模式、运维成熟度和评测结果，而不是把某个产品名当作架构本身。[PostgreSQL 全文检索](https://www.postgresql.org/docs/current/textsearch.html) [pgvector](https://github.com/pgvector/pgvector)

## 本章小结

可信检索从理解原始来源开始，而不是从生成向量开始。不同来源要保留自己的结构；统一知识对象负责携带身份、版本、权限、时间和血缘；搜索索引只是随时可以重建的视图。收到问题后，系统先按权限和任务缩小范围，再选择 BM25、语义、图或实时工具，最后合并结果，并让每条证据都能回到原文。C0–C2 的代码用最小实现验证这些规则始终没有被破坏。下一章不会直接把对象塞进一张图，而是先建立它们必须服从的知识模型，再生成图、Wiki、任务记忆和架构反馈。
