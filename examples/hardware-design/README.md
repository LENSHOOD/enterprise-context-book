# W2 软硬件协同研发示例

虚构企业“澄川设备”准备一款仓储温湿度记录器。本目录保存教学输入、W2-D1软硬件设计草案、预算检查、嵌入式软件主机行为模型和故障测试。完整设计说明见[书中示例](https://lenshood.github.io/enterprise-context-book/cases/hardware-w2)。目录名沿用 `hardware-design`，避免已有引用失效。

所有数值与器件代号均为合成教学数据，不对应真实器件、报价或测试报告。交付范围是可评审设计及Python主机模型，没有原理图、PCB、可刷写固件、真实驱动、CAD、物理测量或量产放行。主机测试不会验证MCU调度、Flash可靠性或射频性能。

## 文件与运行

- `enterprise-brief.md`：企业背景、目标、能力、责任与拟建应用的合成教学设定，供人工建模核对；未纳入工程输入散列，检查器不读取它，也不执行企业关系查询。
- `inputs.json`：六项产品需求、来源版本、功耗/材料预算及固件队列与重试策略，快照为w2-inputs-r2。
- `design.json`：W2-D1 草案、来源快照及内容散列、结构/节奏/接口说明、需求追踪、待做验证与未决项。
- `check_design.py`：Python标准库预算、配置、软件需求分配及引用检查。它不执行主机故障场景、硬件测试或发布批准。
- `tests/test_design.py`：功耗反例、需求违背、输入变化、引用缺失与伪造验证状态的检查。
- `firmware-contract.md`：FW-W2@r1软件约定，说明驱动适配、调度、队列、确认和恢复，以及目标板验证边界。
- `firmware_model.py`：单一事件循环、模拟原子日志和去重接收端；以整数秒驱动，不连接硬件或真实网络。
- `simulate_firmware.py`：使用同一输入和设计绑定运行正常、确认丢失后重启、持续断网三项场景。
- `tests/test_firmware.py`：覆盖队列满、丢确认、错误确认、写入失败、重启、调度延迟等行为。

在仓库根目录执行：

```bash
python3 examples/hardware-design/check_design.py
python3 examples/hardware-design/simulate_firmware.py
python3 -m unittest discover -s examples/hardware-design/tests -v
```

也可用 `--inputs` 和 `--design` 指定文件。退出码 0 表示所选草案通过本检查器覆盖的预算、配置与引用检查；1 表示配置或预算不满足要求；2 表示输入、绑定或引用无效。任何退出码都不表示产品完成物理验证。

软件场景命令也支持 `--inputs` 和 `--design`，先检查相同输入绑定，再运行行为场景。退出码0表示场景断言通过，2表示输入或场景断言失败。是否存在采样缺口，另看各场景的 `sample_quality`，不要只看退出码。

数值输入限制为零（仅适用允许为零的字段）或 10⁻⁹ 至 10⁹，单个数字表示不超过64字符。这是教学计算器的输入边界，不是硬件规范；超范围或计算异常返回受控输入错误。设计章节必须含正文，验证项必须有方法，未决项必须为非空文本列表。

## 默认结果

按 60 秒采样、300 秒上传，24 个月按 17,520 小时计算。事件电量是电池输入端相对于待机的增量，以 μAh 表示；两种候选的整机待机基线均假设为20 μA，采样及暂存每次增加0.02 μAh。

| 候选 | 上传增量电量 | 平均电流 | 期间所需电量 | 材料估值 | 功耗预算 |
|---|---:|---:|---:|---:|---|
| RADIO-A | 8 μAh | 117.2 μA | 2,053.344 mAh | 64 元 | 不通过 |
| RADIO-B | 3 μAh | 57.2 μA | 1,002.144 mAh | 72 元 | 通过 |

可分配容量预算为1,680 mAh，材料上限80元。共同材料48元包含主控、传感器、电源管理、存储、PCB、电池和外壳；无线模块分别增加16或24元。所有值都是假设工况下的教学输入。

默认选择B，输出 `status: draft_ready_for_review`、`physical_verified: false`、`production_release_allowed: false`。所有物理验证仍为 planned，测量指标还有待确认项。

## 软件行为与默认结果

教学策略是32条队列，首次上传失败后等待10秒、再失败后等待20秒，最多3次尝试。记录先提交再发送；收到正确的整批确认后只清理该批记录。重启恢复中的积压记录立即尝试发送，后续采样从启动后60秒重新安排，恢复期间不承诺正常连续采样间隔。

| 场景 | 实际默认输出 |
|---|---|
| 正常600秒 | 10条独立记录、2次发送、未确认队列为0 |
| 丢确认后重启 | 最终10条独立记录、5次重复送达由接收端去重、队列为0 |
| 首个窗口持续断网 | 300/310/330秒共3次尝试，到599秒保留9条记录 |

`host_scenarios_passed`检查行为及样本记账；`sample_quality`报告已提交、队列满、传感器错误和错过周期，`restart_schedule_gap`另报重启重排导致的采样次数差异。队列缩到5条并重新绑定后，断网场景仍可符合“保留旧记录”的策略，但会报告4个缺口及 `all_scheduled_samples_retained: false`。

`firmware_target_verified`、`physical_verified`、`production_release_allowed`始终为false。MemoryJournal复用同一内存对象模拟重启，假设提交全有或全无；没有验证进程重启或Flash掉电原子性。同步通信回调代表一次已完成、有时限的尝试；目标板应拆为完成事件/超时，并补充驱动、调度、协议安全和真实存储测试。

## 改动与验证

将A的上传间隔改为600秒，会降低估算功耗，但违反300秒的上报要求，整体检查仍失败。输入变化后，仅沿用旧快照名也会被内容散列检查拒绝。新一轮设计需要重新确认输入及其版本，更新草案绑定，再重新计算；不能通过忽略失效检查继续使用旧结果。

输入散列采用 UTF-8、排序字段、紧凑分隔符、保留中文的规范化 JSON 做 SHA-256，函数见 `inputs_digest()`。它绑定教学输入内容，不验证来源真实性或授权。检查器限定采样、上传、续航和测量四项软件分配的验证归属，但不能自动证明全部业务含义；这些仍由评审和实际试验完成。

估算使用固定事件电量，未建立重试、积压批次、Flash写入、环境或电池动态的功耗模型。增加软件重试、扩大批次后不能继续以正常每小时12次上传的估算证明寿命；需要重新取得工况输入。进入固件构建、上板联调、试制和量产前还需对应验证。
