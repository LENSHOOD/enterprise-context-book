# 贯穿案例规格 v1.0.0-rc.20

> 文档类别：配套案例的目标、验收范围与当前交付边界。

本规格同时记录目标与当前交付边界；`reviews/run_manifest.json` 是 2026-08-30 的历史审计，不代表当前候选。当前版本、测试和部署状态以仓库提交与 GitHub Actions 为准。

## 案例 A：Northstar Commerce 企业上下文系统

### 目标

用一套可公开、可本地运行的数据，演示企业上下文从原始来源到 Agent 使用的完整生命周期。

### 虚构企业与系统

Northstar Commerce 经营在线订单业务，包含订单、支付、库存、履约和通知服务。团队同时维护产品规则、ADR、Runbook、工单、API Schema、部署配置和多个代码仓。

### 企业级上下文范围

案例的企业上下文内容体系覆盖外部环境与商业模式、战略意图、业务能力与价值流、经营与组织、应用数据和业务运行。MEAF 架构视图帮助组织这些内容之间的关系；Agent 的目标、身份、时间、范围与执行条件由任务上下文表达。身份、时间、权限、血缘、责任和证据治理贯穿资源维护与任务使用。C7 的 context_layers 使用 L0—L6 作为输出导航标签，便于定位不同内容分组。

### 三层范围

案例始终区分三层。**目标企业**包含订单、支付、库存、履约和通知五个逻辑服务；**教学 fixture**只保留回答验收题所需的最小对象和关系；**生产化扩展**列出真实系统需要但本仓库不交付的能力。书稿不得把任一层的能力写成另一层已经实现的事实。

### 公开数据集

- 以 3 个代码消费者和 1 个逻辑仓对象表示代码范围（教学 fixture，部分达成）；
- 5 份可人工阅读的原始来源 fixture（政策、Runbook、事件、代码与测试），可经 `src/build_baseline.py` 重建 C1 基线对象；
- 能力问题、术语表、限界上下文、实体与关系契约、源映射四类可评审建模输入，可经 `src/build_domain_model.py` 重建并验证 C3 领域模型；所有声明元素都由 fixture 实例化，时间关系保留时间信封；
- 产品规则、事件 Schema、服务、API、团队、Runbook、ADR 与事故对象（达成最小闭环）；
- 企业架构应用视图声明及其与实现、运行证据的三类差异 fixture（达成最小闭环）；
- 4 类运行与工程角色、4 类战略读取角色、第二租户与对象级 ACL（达成教学范围）；
- C7 独立的已结算战略快照，包含商业模式、外部环境、指标、目标、能力、价值流、流程、组织、应用、数据产品、运行观察和候选事件（达成教学建模；非实时数据仓）；
- 27 条 Golden Questions，按 10 个评测主题检查必要或禁止证据；其中 3 条覆盖 C7 的口径确认、战略分析和权限边界（达成教学下限）；
- OpenAPI/Protobuf 与 Kubernetes 配置、真实工单历史（未交付，属于生产化扩展）。

### 必须回答的任务

1. 订单取消流程如何工作？
2. 修改取消事件会影响哪些仓库、消费者和测试？
3. 退款积压告警应怎样排查？
4. 当前规则与历史 ADR 为什么冲突，哪一份仍有效？
5. 哪些结论来自代码、Runbook、业务系统或模型推断？
6. 不同角色看到的答案和证据有何差异？
7. 企业架构声明与代码、运行观察有哪些一致、待核验和未声明关系？
8. C-level 询问 H2 销售为什么低于 H1 时，系统能否先确认指标口径，再把差异连接到战略目标、业务能力、组织、应用、数据产品和待验证事件？

### 角色与动作交接

- `support`：读取面向客服的政策与本租户可见状态；
- `developer`：读取代码、ADR 与工程资料；
- `sre`：读取运行与工程证据，开始诊断、准备动作、执行和验证；
- `incident_commander`：读取运行状态和动作预览，并对特定参数散列确认或拒绝；
- `executive` / `strategy` / `revops` / `product`：读取 C7 企业级战略快照，先确认指标契约，再输出只读分析复核建议；当前 fixture 对四类角色共享同一只读快照，生产系统还需按组织范围过滤对象和指标；
- 第二租户用于验证同一对象标识不会穿透租户边界。

任务记忆按租户和任务操作者隔离；实时观察必须在 TTL 内；动作预览绑定观察 revision；执行回执只能由服务端发行，并且只能在 `verifying` 状态下验证。

事故处置采用 **SRE -> incident_commander -> SRE** 交接。确认令牌绑定预览中的参数散列和被指定的 SRE；负责人不因确认而获得代码或 Runbook 访问权，也不直接执行动作。

`resolved` 只表示本次模拟动作满足有限观察规则，不证明积压清空、根因修复或退款到账。观察来自同一模拟状态；Web 应用已持久保存任务和核心运行状态，但独立业务验证与拒绝后的同任务重新诊断入口仍未实现。C3 验证人工对象与关系的契约和连通支持，不核验引用真实性；C7 独立校验经营快照，不复用 C3 的能力问题连通子图门。

### 本地工作台与交互教程

- VitePress 的工作台和章节实验共享 Vue 组件，通过本机同源 HTTP 调用原有 Python 核心，无任意 shell 入口。
- SQLite 按 Cookie 对应的独立空间保存任务条件、上下文快照、工作事件、模拟队列、预览、批准与回执；事务保护本地并发与幂等，不覆盖外部业务副作用。
- 任务创建、口径确认、笔记和人工复核适用于相应工作线；事故负责人仅能读取预览，不能读取操作者的完整包。
- 政策更新修改私有副本，重新编译校验并更新版本；检索和 Wiki 使用新对象，旧任务快照保留并标记需重新取证。已有动作预览的事故任务必须新建。
- 公开站的示例来自构建时执行，明确标注非当前请求结果；本地服务才能实际运行。源码片段由 AST 从实际文件提取，页面与执行版本不一致时禁止启动实验。
- 模拟身份、显式推进的教学时钟、完整空间 JSON 保存与小规模 fixture 是教学边界；没有公网部署、模型智能体、生产认证、通用任务调度、增量依赖队列和独立业务传感器。
- 验收包括重启恢复、并发重试、角色与空间隔离、参数绑定、过期/拒绝、资源更新传播、静态路径隔离和同源请求检查。

### 构建阶段

1. C0：检查原始来源及其范围；
2. C1：将来源编译为统一对象、版本、时间、来源和 ACL，并验证 BM25；
3. C2：在同一对象契约上加入离线语义代理、RRF 和时间选择；
4. C3：从能力问题、术语、概念模型和源映射编译领域模型，并以实际对象、时间边和连通答案子图验证契约；
5. C4：把能力问题所需关系编译为遍历边界，支持保留语义方向的正反向导航，再加入模板 Wiki、架构声明一致性检测与资源更新实验；
6. C5：保存任务条件，把选中的能力问题与相关语义切片装入 Context Package，并加入工具可见性、观察、快照和工作记录；
7. C6：验证 SRE 诊断、负责人确认、SRE 执行与结果验证；
8. C7：通过统一的 `NorthstarPlatform.context(mode="strategic")` 提供只读战略分析包；第一次请求只返回待确认的指标契约，确认后输出指标语义、H1/H2 分解、企业级上下文、证据支持的假设和数据缺口；不直接下因果结论或执行经营动作；四个维度分解必须分别回到同一公司总额，不能跨维度相加；
9. 将模型治理工作流、PostgreSQL/pgvector、真实连接器、Tree-sitter、SCIP、MCP/REST 与持续评测作为生产替换路线。

### 可复现标准

Docker Compose 一键验证；固定依赖版本；书中标为“可复现”的命令必须重复执行；删除 `generated/` 后，C1 能从 `data/raw/` 重建基线，C3 能从 `data/modeling/` 重建领域模型和实例验证报告；fixture 和预期证据公开；无商业 API 也可本地运行。`npm run lab` 构建书站并启动本地接口。规模化基础设施、生产接口与正式模型评审系统不属于当前教学系统的完成声明。

## 案例 B：Linux 内核子系统知识库

### 目标

建立一个作者可长期使用的 Linux 源码研究工具，并把它作为代码知识库架构的真实规模与复杂度测试。

### 第一版范围

第 18 章已选择 eBPF，固定上游 `v6.12` 的 Git 提交，不复制源码进书籍仓库。番外另记录完整内核的 SQLite 摄取与查询实验。两者加深源码资源建设，不交付完整企业平台。

### 当前知识产物

- 按明确路径范围摄取文件，正则抽取函数、类型、BPF 命令与候选调用；
- 文件级符号地图与固定提交、路径、定义行引用；
- 子系统内 BM25、有界出边，以及全仓 SQLite/FTS5 检索；
- 文件、节点、边、未解析候选的计数与警告，不提供已标注的准确率；
- 全仓历史容量记录与后续增量方案。

构建配置、维护关系、机制级 Wiki、向量通道、Tree-sitter 和编译级解析属于扩展目标。名称唯一匹配是启发式证据，不等于编译器证明调用。以下问题用于引导扩展；当前查询只返回部分源码入口，不保证回答完整机制。

### 验收问题示例

- 一个核心机制从用户入口到内核实现经历哪些路径？
- 某结构或回调在哪里定义、注册并被调用？
- 修改目标符号可能影响哪些模块与配置？
- Wiki 陈述能否回到固定版本的源码证据？
- Tree-sitter 候选关系与编译级精确关系在哪里不同？

## 示例 C：W2 软硬件协同设计草案

### 目标与交付

虚构企业澄川设备基于 W1 约束，为仓储温湿度记录器 W2 形成新的软硬件设计草案。产物包括硬件框图、BOM和功耗预算，以及嵌入式软件模块、调度、队列、确认与异常恢复、需求追溯和验证计划，集中说明见 `book/cases/hardware-w2.md`。

### 可运行范围

`examples/hardware-design/inputs.json` 保存合成教学输入，`design.json` 保存 W2-D1 草案及输入内容绑定，`check_design.py` 使用 Python 标准库复算电池输入端的增量电量预算与材料估值，并检查需求、设计和验证引用。它不调用模型、不设计电路、不执行物理测试、不批准发布。

FW-W2@r1 软件契约规定32条队列及10/20秒退避等教学选择，参数纳入w2-inputs-r2绑定；四项软件需求分配覆盖采样、上传、续航和测量。`firmware_model.py` 实现Python主机行为，`simulate_firmware.py` 运行正常、丢确认后重启和持续断网场景，报告独立记录、重复送达与采样缺口。日志原子提交、整批确认和接收端去重为模型假设；不包含真实驱动、Flash、RTOS或网络安全实现。

`enterprise-brief.md` 另行提供 BRIEF-W2@r2 企业教学背景，包含客户价值、商业模式、目标和指标草案、举措、能力、价值流、角色责任及拟建应用。第四、六、七、八章共同使用这份来源，企业关系由读者人工核对。文件不属于 w2-inputs-r2 的计算输入散列，现有程序不读取它、不执行企业关系查询，也未部署拟建应用；经营效果仍缺少真实维护记录和确认后的指标口径。

默认60秒采样、300秒上传，目标期间17,520小时，可分配电量预算1,680mAh。A候选平均电流117.2μA、期间电量2,053.344mAh、材料64元；B为57.2μA、1,002.144mAh、72元。B仅通过教学初筛；物理验证与生产放行标志始终为false，测量范围和误差仍有待确认项。

### 验收与边界

检查应拒绝旧输入绑定、缺失或错误的软件验证归属、伪造物理测试通过，以及用延长上报周期掩盖功耗超标。行为测试覆盖错误确认、确认丢失、存储失败、队列满、旧批次与新采样隔离、重启与延迟。队列满会丢弃新样本并报告缺口；重启优先发送已存数据，但重新安排采样，不保证停机期间的正常采样间隔。测试、预算和场景复现纳入 `npm test` 和 Pages CI；firmware_target_verified及物理验证/生产放行均为false。

没有真实器件、报价、PCB、可刷写固件、CAD、样机或量产验证。正常工况预算没有覆盖软件重试、Flash写入与积压批次的实际耗电。本例不改变Northstar的接口与测试。
