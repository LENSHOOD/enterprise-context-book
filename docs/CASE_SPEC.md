# 贯穿案例规格 v1.0.0-rc.3

> 文档类别：配套案例的目标、验收范围与当前交付边界。

本规格同时记录目标与当前交付边界；发布状态以 `reviews/run_manifest.json` 的 `verdict` 为准。

## 案例 A：Northstar Commerce 企业上下文系统

### 目标

用一套可公开、可本地运行的数据，演示企业上下文从原始来源到 Agent 使用的完整生命周期。

### 虚构企业与系统

Northstar Commerce 经营在线订单业务，包含订单、支付、库存、履约和通知服务。团队同时维护产品规则、ADR、Runbook、工单、API Schema、部署配置和多个代码仓。

### 三层范围

案例始终区分三层。**目标企业**包含订单、支付、库存、履约和通知五个逻辑服务；**教学 fixture**只保留回答验收题所需的最小对象和关系；**生产化扩展**列出真实系统需要但本仓库不交付的能力。书稿不得把任一层的能力写成另一层已经实现的事实。

### 公开数据集

- 以 3 个代码消费者和 1 个逻辑仓对象表示代码范围（教学 fixture，部分达成）；
- 5 份可人工阅读的原始来源 fixture（政策、Runbook、事件、代码与测试），可经 `src/build_baseline.py` 重建 C1 基线对象；
- 产品规则、事件 Schema、服务、API、团队、Runbook、ADR 与事故对象（达成最小闭环）；
- 企业架构应用视图声明及其与实现、运行证据的三类差异 fixture（达成最小闭环）；
- 4 类角色、第二租户与对象级 ACL（达成）；
- 24 条 Golden Questions，覆盖 9 类任务并绑定必要或禁止证据（达成教学下限）；
- OpenAPI/Protobuf 与 Kubernetes 配置、真实工单历史（未交付，属于生产化扩展）。

### 必须回答的任务

1. 订单取消流程如何工作？
2. 修改取消事件会影响哪些仓库、消费者和测试？
3. 退款积压告警应怎样排查？
4. 当前规则与历史 ADR 为什么冲突，哪一份仍有效？
5. 哪些结论来自代码、Runbook、业务系统或模型推断？
6. 不同角色看到的答案和证据有何差异？
7. 企业架构声明与代码、运行观察有哪些一致、待核验和未声明关系？

### 角色与动作交接

- `support`：读取面向客服的政策与本租户可见状态；
- `developer`：读取代码、ADR 与工程资料；
- `sre`：读取运行与工程证据，开始诊断、准备动作、执行和验证；
- `incident_commander`：读取运行状态和动作预览，并对特定参数散列确认或拒绝；
- 第二租户用于验证同一对象标识不会穿透租户边界。

事故处置采用 **SRE -> incident_commander -> SRE** 交接。确认令牌绑定预览中的参数散列和被指定的 SRE；负责人不因确认而获得代码或 Runbook 访问权，也不直接执行动作。

### 构建阶段

1. C0：检查原始来源及其范围；
2. C1：将来源编译为统一对象、版本、时间、来源和 ACL，并验证 BM25；
3. C2：在同一对象契约上加入离线语义代理、RRF 和时间选择；
4. C3：加入关系图、分层 Wiki、任务记忆和架构声明一致性检测；
5. C4：组装 Context Package、工具可见性与实时观察；
6. C5：验证 SRE 诊断、负责人确认、SRE 执行与结果验证；
7. 将 PostgreSQL/pgvector、真实连接器、Tree-sitter、SCIP、MCP/REST 与持续评测作为生产替换路线。

### 可复现标准

Docker Compose 一键验证；固定依赖版本；书中标为“可复现”的命令必须重复执行；删除 `generated/` 后 C1 能从 `data/raw/` 重新生成基线；fixture 和预期证据公开；无商业 API 也有本地降级路径。规模、外部数据库与服务接口不属于当前教学原型的完成声明。

## 案例 B：Linux 内核子系统知识库

### 目标

建立一个作者可长期使用的 Linux 源码研究工具，并把它作为代码知识库架构的真实规模与复杂度测试。

### 第一版范围

在样章原型阶段比较 eBPF 与调度器，依据源码边界、解析覆盖、学习价值和可演示问题确定一个。固定 Linux 上游 release/tag，不复制源码进书籍仓库。

### 知识产物

- 子系统目录、文件、符号、调用、依赖和配置图；
- 子系统→模块→文件→符号的层级 Wiki；
- 源码、文档和摘要的 BM25/向量/图检索；
- `repository + tag/commit + path + lines` 引用；
- 解析精度、未解析关系和置信度报告；
- 扩展到全内核的容量与增量方案。

### 验收问题示例

- 一个核心机制从用户入口到内核实现经历哪些路径？
- 某结构或回调在哪里定义、注册并被调用？
- 修改目标符号可能影响哪些模块与配置？
- Wiki 陈述能否回到固定版本的源码证据？
- Tree-sitter 候选关系与编译级精确关系在哪里不同？
